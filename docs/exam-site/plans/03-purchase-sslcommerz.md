## Slice 1 — Prices

`V32__live_exam_purchase.sql` adds a nullable price to the module and the exam:

```sql
ALTER TABLE live_exam_modules ADD COLUMN price NUMERIC(12, 2) NULL;
ALTER TABLE live_exams ADD COLUMN price NUMERIC(12, 2) NULL;

ALTER TABLE live_exam_modules
    ADD CONSTRAINT live_exam_modules_price_check CHECK (price IS NULL OR price > 0);
ALTER TABLE live_exams
    ADD CONSTRAINT live_exams_price_check CHECK (price IS NULL OR price > 0);
```

A null price means the item is not for sale. The module price is not the sum of its exams. Currency is BDT. There is no second currency.

`LiveExamModuleService.rejectLockedFields` stops rejecting `price`. When `price` is present on create or patch, the caller must have `EXAM_PRICE`. That permission is already Master Admin only. A System Admin receives `403`. A student receives `403`. A price of `0` or below is `400` `VALIDATION_FAILED`. A JSON `null` clears the price.

The same rule is added to the live exam create and patch. `courseId` stays rejected.

The public module and public exam payloads gain `price`. A null price is omitted, which is how this API writes nulls. Questions, options, and PDF bytes stay off the public read. Staff reads gain `price` as well.

## Slice 2 — Orders and the gateway

The same migration adds the order and the grant.

```sql
CREATE TABLE live_exam_orders (
    id           UUID PRIMARY KEY,
    student_id   UUID NOT NULL REFERENCES users (id),
    scope        VARCHAR(8) NOT NULL,
    module_id    UUID NOT NULL REFERENCES live_exam_modules (id),
    exam_id      UUID NULL REFERENCES live_exams (id),
    amount       NUMERIC(12, 2) NOT NULL,
    currency     CHAR(3) NOT NULL,
    method       VARCHAR(16) NOT NULL,
    tran_id      VARCHAR(30) NOT NULL,
    status       VARCHAR(16) NOT NULL,
    val_id       VARCHAR(128) NULL,
    created_at   TIMESTAMPTZ NOT NULL,
    updated_at   TIMESTAMPTZ NOT NULL,
    CONSTRAINT live_exam_orders_scope_check CHECK (
        (scope = 'MODULE' AND exam_id IS NULL)
        OR (scope = 'EXAM' AND exam_id IS NOT NULL)
    ),
    CONSTRAINT live_exam_orders_status_check CHECK (
        status IN ('INITIATED', 'SUCCEEDED', 'FAILED', 'CANCELLED')
    ),
    CONSTRAINT live_exam_orders_amount_check CHECK (amount > 0),
    CONSTRAINT live_exam_orders_currency_check CHECK (currency = 'BDT'),
    CONSTRAINT live_exam_orders_method_check CHECK (method = 'SSLCOMMERZ'),
    CONSTRAINT live_exam_orders_tran_id_unique UNIQUE (tran_id)
);

CREATE UNIQUE INDEX live_exam_orders_open_module_unique
    ON live_exam_orders (student_id, module_id) WHERE status = 'INITIATED' AND scope = 'MODULE';
CREATE UNIQUE INDEX live_exam_orders_open_exam_unique
    ON live_exam_orders (student_id, exam_id) WHERE status = 'INITIATED' AND scope = 'EXAM';

CREATE TABLE live_exam_grants (
    id          UUID PRIMARY KEY,
    student_id  UUID NOT NULL REFERENCES users (id),
    scope       VARCHAR(8) NOT NULL,
    module_id   UUID NOT NULL REFERENCES live_exam_modules (id),
    exam_id     UUID NULL REFERENCES live_exams (id),
    order_id    UUID NOT NULL UNIQUE REFERENCES live_exam_orders (id),
    created_at  TIMESTAMPTZ NOT NULL,
    CONSTRAINT live_exam_grants_scope_check CHECK (
        (scope = 'MODULE' AND exam_id IS NULL)
        OR (scope = 'EXAM' AND exam_id IS NOT NULL)
    )
);

CREATE UNIQUE INDEX live_exam_grants_module_unique
    ON live_exam_grants (student_id, module_id) WHERE scope = 'MODULE';
CREATE UNIQUE INDEX live_exam_grants_exam_unique
    ON live_exam_grants (student_id, exam_id) WHERE scope = 'EXAM';
```

`tran_id` is generated by this API and is at most 30 characters, which is the gateway's limit. `amount` is the price at the moment of initiation. A later price edit does not rewrite it.

`POST /api/v1/live-exam-orders` is student-only.

```json
{ "moduleId": "..." }
{ "examId": "..." }
```

Both ids, or neither, is `400` `VALIDATION_FAILED`. The target must be published, and its category branch must be open. A draft or an archived branch is `404`. A null price is `409` `PRICE_REQUIRED`. An undated exam is allowed. A roster row or an existing grant for that target is `409` `ALREADY_PURCHASED`. An `INITIATED` order for the same student and target is returned again, with the same `tranId` and amount. A second initiate that loses a race on the open-order index re-reads and returns that order. The response is `201` on the first call and `200` on that repeat:

```json
{ "orderId": "...", "tranId": "...", "status": "INITIATED", "amount": "500.00", "redirectUrl": "..." }
```

`LiveExamPaymentGateway` has two methods: `start`, which returns the redirect URL, and `verify`, which accepts the callback fields and returns valid, invalid, or unreachable. `SslCommerzGateway` is created only when `SSLCZ_STORE_ID`, `SSLCZ_STORE_PASSWORD`, `SSLCZ_BASE_URL`, and `SSLCZ_CALLBACK_BASE_URL` are all set. The plan does not contain those values and does not choose the sandbox host or the live host. `SSLCZ_CALLBACK_BASE_URL` is the public origin used to build the return and IPN URLs. This repo does not own that hostname. When the bean is absent, initiate returns `503` `PAYMENT_GATEWAY_UNAVAILABLE`. Tests register a fake as the primary bean, so the suite never calls SSLCommerz and never sees that `503`.

The success, fail, cancel, and IPN URLs sent to the gateway are under this API and include the `tranId`. They are `permitAll`. A browser session is not required.

```
POST /api/v1/live-exam-orders/{tranId}/return
POST /api/v1/live-exam-orders/{tranId}/ipn
```

`return` carries `success`, `fail`, or `cancel`. `ipn` is the server notice. Both look up the order by `tranId`. A body `tran_id` that does not match the path is `400`. An unknown `tranId` is `404`.

A `success` or an IPN calls `verify`. Access is written only when `verify` returns valid and the validated amount, currency, and `tran_id` match the order. The browser redirect alone does not grant access. `verify` unreachable leaves the order `INITIATED` and returns `503`, so a later notice can retry. `verify` invalid sets `FAILED` and grants nothing.

A `fail` sets `FAILED`. A `cancel` sets `CANCELLED`. Neither grants access. A later verified success on that same order still moves it to `SUCCEEDED` and writes the grant. A verified success wins over an earlier cancel.

The grant insert and the status change are one transaction. A module order writes a `MODULE` grant. An exam order writes an `EXAM` grant and stores that exam's module id. A second verified call for an order that is already `SUCCEEDED` returns `200` and does not insert a second grant. The unique `order_id` on the grant is the backstop.

`GET /api/v1/live-exam-orders/{id}` returns the caller's own order. Another student's order is `404`.

`POST /api/v1/live-exam-orders/{id}/cancel` is the student, and only while the order is `INITIATED`. It sets `CANCELLED` and grants nothing. A later initiate then uses the current price. A `SUCCEEDED` order cannot be cancelled here. A module grant blocks a new exam checkout in that module, because access already exists. An exam grant does not block a later module checkout.

Only the Master Admin can mark a pending order paid, through `POST /api/v1/live-exam-orders/{id}/confirm` (the R-8 path), or reject it. A Master Admin who must enrol someone without payment uses a manual grant. A System Admin has no order write and sees the list read-only. Course and book payments are out of this delivery: do not use `PAYMENT_VERIFY` on live exam orders, and do not alter `payments` or `exam_module_purchases`. `access_mode` stays `MANUAL`.

## Slice 3 — The grant beside the roster

One check, `hasAccess(studentId, exam)`, is true when any of these holds:

- a roster row for the exam's module
- a `MODULE` grant for that module
- an `EXAM` grant for that exam

A module grant covers an exam published after the payment. The grant stores the module id, not a list of exam ids. An exam grant does not cover a sibling exam.

These reads use that check. A miss stays `404`, as a missing roster does today.

- `LiveExamService.get` for a student
- `LiveExamService.list` for a student, limited to exams the student can access
- `LiveExamModuleService.getPublished`
- `LiveExamModuleService.list` for a student, through `findVisibleToStudent`
- `LiveExamRepository.findVisibleRoutineCandidates`

Take exam, the question PDF, and the MCQ later attempt already go through `get`, so they follow the same check. The window rules do not change. An undated exam still returns `409` `SITTING_NOT_OPEN`. A written exam still has no later attempt.

The public catalog does not use this check.

## Tests

New `LiveExamPurchaseIT` on PostgreSQL. Do not use H2. The fake gateway is the only gateway in this class. Run `mvn test "-Dtest=LiveExamPurchaseIT,LiveSittingIT,LiveExamIT,LivePublicCatalogIT"`.

- A Master Admin sets a module price and an exam price. A System Admin receives `403`. The public exam and module reads return those prices and still have no questions.
- A student initiates an exam order and a module order. The amount is the price at that moment. A second initiate returns the same `tranId`. A missing price is `409` `PRICE_REQUIRED`. A draft exam is `404`.
- A verified success writes one grant. The same notice again returns `200` and the grant count stays one. An invalid verification sets `FAILED` and writes no grant. A cancel writes no grant. A verified success after that cancel writes the grant.
- An unreachable verification leaves `INITIATED` and returns `503`.
- With no grant, Take exam is `404` and the question PDF is `404`. With a roster row, Take exam is allowed and the question PDF is served until the sitting deadline. With an exam grant, that exam is allowed and a sibling exam is `404`. With a module grant, an exam created after the payment is allowed.
- An undated purchased exam stays on the module list. Take exam returns `409` `SITTING_NOT_OPEN`.
- A student who already has a grant receives `409` `ALREADY_PURCHASED` on initiate. Cancelling their own `INITIATED` order grants nothing, and the next initiate uses the current price. A `SUCCEEDED` order rejects that cancel.
- The personal routine lists a granted exam whose window has not ended, and omits an undated one.
